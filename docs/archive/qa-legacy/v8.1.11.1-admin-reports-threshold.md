# V8.1.11.1 — QA de notificação admin por limiar de denúncias

## Arquitetura aplicada
- Estratégia A (tempo real): `public.reports` (`AFTER INSERT`) chama `public.notify_admin_if_reports_threshold(post_id)`, que envia HTTP para a Edge Function `notify-admin-reports-threshold`.
- Limiar: `3` denúncias abertas (`status='open'`) por post.
- Canal: webhook (URL em secret).
- Anti-spam: no máximo 1 notificação por post dentro da janela `REPORTS_NOTIFY_COOLDOWN_HOURS` (default `24h`), persistido em `public.audit_log` com ação `reports_threshold_notified`.

## Segurança aplicada
- Função Edge usa `SUPABASE_SERVICE_ROLE_KEY` (server-side).
- Entrada validada: `post_id` obrigatório e UUID.
- Trigger assina payload com HMAC (`x-kc-signature` + `x-kc-timestamp`).
- A função rejeita assinatura inválida/expirada.
- Payload de notificação não inclui `reporter_id`, e-mail do denunciante, nem `details`.

## Setup
1. Deploy da função:
```bash
supabase functions deploy notify-admin-reports-threshold
```

2. Definir secrets da função:
```bash
supabase secrets set SUPABASE_URL=https://<PROJECT_REF>.supabase.co
supabase secrets set SUPABASE_SERVICE_ROLE_KEY=<SERVICE_ROLE_KEY>
supabase secrets set KC_APP_BASE_URL=https://<DOMINIO_PRODUCAO>
supabase secrets set ADMIN_REPORTS_WEBHOOK_URL=<WEBHOOK_URL>
supabase secrets set KC_NOTIFY_HMAC_SECRET=<SEGREDO_FORTE_32+>
supabase secrets set REPORTS_THRESHOLD=3
supabase secrets set REPORTS_NOTIFY_COOLDOWN_HOURS=24
```

3. Definir settings no banco (fora do git):
```sql
alter database postgres set app.settings.kc_notify_function_url =
  'https://<PROJECT_REF>.functions.supabase.co/notify-admin-reports-threshold';

alter database postgres set app.settings.kc_notify_function_auth_token =
  '<SERVICE_ROLE_KEY>';

alter database postgres set app.settings.kc_notify_hmac_secret =
  '<MESMO_SEGREDO_DE_KC_NOTIFY_HMAC_SECRET>';
```

## Teste manual (evidência)
1. Escolher um post:
```sql
select id, legacy_id, title
from public.posts
order by created_at desc
limit 1;
```

2. Pegar 4 perfis distintos para simular denunciantes:
```sql
select id
from public.profiles
order by created_at asc
limit 4;
```

3. Inserir 3 denúncias abertas para o mesmo `post_id`:
```sql
insert into public.reports (post_id, reporter_id, reason, details, status) values
  ('<POST_UUID>'::uuid, '<REPORTER_1_UUID>'::uuid, 'spam', null, 'open'),
  ('<POST_UUID>'::uuid, '<REPORTER_2_UUID>'::uuid, 'scam', null, 'open'),
  ('<POST_UUID>'::uuid, '<REPORTER_3_UUID>'::uuid, 'spam', null, 'open');
```

4. Validar:
- Logs da função `notify-admin-reports-threshold` mostram execução `notified=true`.
- Webhook recebeu mensagem com:
  - link do post (`.../product.html?id=...`)
  - contador de denúncias abertas
  - resumo de motivos (ex.: `spam: 2, scam: 1`)
  - sem dados de denunciante.

5. Anti-spam (4ª denúncia):
```sql
insert into public.reports (post_id, reporter_id, reason, details, status) values
  ('<POST_UUID>'::uuid, '<REPORTER_4_UUID>'::uuid, 'other', null, 'open');
```
- Esperado: função retorna `skipped=cooldown_active` (ou equivalente), sem novo envio de webhook.

6. Confirmar marca de notificação no audit log:
```sql
select created_at, action, entity_type, entity_id, payload
from public.audit_log
where action = 'reports_threshold_notified'
  and entity_type = 'posts'
  and entity_id = '<POST_UUID>'::uuid
order by created_at desc;
```

## Checklist de validação
- [ ] Recebeu 1 notificação ao atingir 3+ reports abertos.
- [ ] Notificação contém link + resumo de reasons.
- [ ] Não contém PII desnecessária.
- [ ] 4ª denúncia não gerou spam dentro da janela.
- [ ] `audit_log` registrou `reports_threshold_notified`.
